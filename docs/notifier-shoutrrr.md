# 告警通知改用 shoutrrr 并接入 ntfy

## 问题陈述

订阅源抓取遇到业务错误（上游 403、404 等）时，RSSGen 会熔断该 feed 并发出告警。目前告警只能发到飞书：通知模块里只有一个手写的飞书发送器，按配置中的 `type` 字段分派，新增一个渠道就要新写一个发送器、新增一组专属配置字段。

维护者在同一台设备上自建了 ntfy，希望告警也能推到手机上，并且以后在飞书和 ntfy 之间切换或并用时不必改代码。

配置里还残留着一个 `service_urls` 字段，示例写的是 apprise 风格的 `tgram://...`，注释说明「兼容旧配置，仅打日志」，但实际上没有任何代码读取它。这是一个看起来能用、其实不生效的配置项。

## 解决方案

通知模块改用 Go 生态中与 apprise 对应的库 shoutrrr，采用其仍在维护的分支 `github.com/nicholas-fedor/shoutrrr`。原版 `containrrr/shoutrrr` 自 2023 年 v0.8.0 之后再未发版，且不支持飞书。

每个通知目标用一条 URL 描述，写在 `notifier.service_urls` 下：飞书写成 `lark://open.feishu.cn/<webhook_id>?secret=<签名密钥>`，ntfy 写成 `ntfy://<host>/<topic>?token=...&title=...&priority=...&tags=...`。增删渠道只需改配置。旧的 `services` 列表（`type`、`webhook_url`、`secret`）整体删除，不做兼容。

ntfy 的标题、优先级、标签全部写在 URL 里，代码只发送消息正文。推荐的固定值为：标题 `RSSGen 订阅源获取失败`、优先级 `4`、标签 `warning`、topic `RSSGen`。这些值以配置示例的形式给出，不写死在代码里，原因见实现决策。

## 用户故事

1. 作为维护者，我希望 feed 被业务错误熔断时手机能收到 ntfy 推送，以便不用盯着飞书也能及时知道订阅源坏了。
2. 作为维护者，我希望告警推送的优先级足够高，能在手机上强提醒，以便不被普通通知淹没。
3. 作为维护者，我希望 ntfy 告警带有固定标题和警告标签，以便在通知列表里一眼认出这是 RSSGen 的故障告警。
4. 作为维护者，我希望飞书告警的内容与外观和现在保持一致，以便切换实现后飞书那边没有可感知的变化。
5. 作为维护者，我希望飞书与 ntfy 可以同时启用，同一条告警两边都能收到，以便有冗余。
6. 作为维护者，我希望只启用其中一个渠道也能正常工作，以便按需取舍。
7. 作为维护者，我希望每个通知目标都用一条 URL 描述，以便增删渠道只改配置不改代码。
8. 作为维护者，我希望访问自建 ntfy 时用 access token 鉴权，以便 topic 不对匿名用户开放。
9. 作为维护者，我希望 RSSGen 通过 Docker 内部网络直连 ntfy 容器，以便告警不绕外网、不受宿主机代理影响。
10. 作为维护者，我希望 `service_urls` 中有写错的 URL 时 RSSGen 启动直接失败并指出是哪一条，以便配置错误在部署时暴露，而不是等到真出故障、告警发不出去时才发现。
11. 作为维护者，我希望某个渠道发送失败时日志里能看到失败原因，并且不影响其他渠道继续发送，以便排查且不丢告警。
12. 作为维护者，我希望告警发送不阻塞 feed 请求和后台刷新，以便通知渠道慢或挂了不会拖垮主流程。
13. 作为维护者，我希望关闭通知（`enabled: false`）时完全不发送，即使 `service_urls` 非空，以便临时静默告警。
14. 作为维护者，我希望配置示例和 README 给出飞书与 ntfy 的完整 URL 写法，以便照抄就能用。
15. 作为维护者，我希望 README 说明如何让 RSSGen 容器加入 ntfy 所在的 Docker 网络，以便不必自己摸索 compose 的 external network 写法。
16. 作为维护者，我希望配置里不再残留不生效的字段，以便配置文件所写即所得。
17. 作为维护者，我希望升级后旧的 `services` 写法不再被支持，并在升级说明中写明，以便我知道必须迁移配置。

## 实现决策

**选用 shoutrrr 根包，而非手写 ntfy 发送器。** 曾比较过三种方案：手写 ntfy 发送器（零依赖）、只 import shoutrrr 的单个服务包、import 根包用 URL 分派。维护者选择了根包方案，换取「渠道全靠 URL 配置」的扩展性。实测代价（aarch64，`CGO_ENABLED=0 -ldflags="-s -w"`，与 Dockerfile 一致）：二进制从 16.81 MiB 增至 19.06 MiB，即 **+2.25 MiB（+13.4%）**。只 import ntfy 与 lark 两个服务包仅增加 128 KiB，但那样就失去了 URL 分派。

**飞书改走 shoutrrr 的 lark 服务，删除手写的飞书发送器。** lark 服务支持 `open.feishu.cn` 域名、`secret` 签名，以及对飞书响应体中 `code != 0` 的错误判定，覆盖了现有飞书发送器的全部行为。URL 路径部分就是 webhook 地址 `/open-apis/bot/v2/hook/` 后面那段 ID。lark 服务只接受 `open.feishu.cn` 与 `open.larksuite.com` 两个主机名。

**代码只发送正文，不向 shoutrrr 传任何发送参数。** shoutrrr 的路由会把同一份发送参数原样交给每个服务，而每个服务遇到自己未声明的参数名会直接返回错误（v0.22.0 的属性键解析器返回 `ErrInvalidConfigKey`）。lark 只声明了 `secret`、`title`、`link`，若在代码里统一传入 `priority`、`tags`，飞书那一路每次都会发送失败。两边都认 `title`，但 lark 收到标题后会把消息从纯文本切换为带标题的富文本，改变飞书的外观。因此 ntfy 专属的标题、优先级、标签全部放进 ntfy 的 URL 查询参数。

**消息正文格式不变。** 继续沿用现有格式：首行 `[RSSGen] 订阅源 <feed 键> 获取失败`，其后是状态码、错误、时间。ntfy 上首行与标题有重复，这是可接受的，不为单个渠道单独拼接正文。

**配置结构。** `notifier` 下保留 `enabled`、`business_error_codes`，`service_urls` 改为真正生效的通知目标列表。删除 `services` 及其元素类型，删除通知模块配置中的服务配置类型与旧字段注释。不对旧写法做任何兼容或迁移提示，升级说明写入 README。

**启动时校验，非法 URL 直接失败。** 通知器在构建运行时阶段用 shoutrrr 根据全部 URL 一次性创建发送路由，任何一条解析失败都让构建返回错误，错误信息指出出错的那条 URL 的序号与原因，不得输出 URL 原文，因为其中含 token 与签名密钥。为此通知器的构造函数改为同时返回错误，由运行时构建函数向上传递。`enabled: false` 时不创建路由、不校验 URL。

**发送行为。** 保持异步发送、不阻塞调用方。路由对每个服务分别返回结果，失败的逐条以错误级日志记录，日志中同样不得出现 URL 原文。shoutrrr 自身的日志输出不接入。超时采用路由默认值（每个服务的发送预算，下限为库的默认超时），不额外配置。

**对外接口不变。** 通知器对调用方暴露的「按 feed 键、状态码、错误信息发出告警」方法签名不变，熔断、健康状态、刷新器等调用方无需改动。

**部署：RSSGen 加入 ntfy 所在网络。** ntfy 运行在同一台设备上的另一个 compose 项目中，容器名为 `ntfy`，容器内监听 80 端口（宿主机映射到 7921）。不同 compose 项目默认处于不同网络，RSSGen 无法按容器名解析到 ntfy。方案是在 RSSGen 的 compose 中把 ntfy 所在网络声明为 external 网络并让 rssgen 服务加入，URL 写 `ntfy://ntfy/RSSGen?scheme=http&...`。仓库内的 compose 文件不写死该网络，因为网络名随各自部署而变；只在 README 中给出示例。rssgen 容器未设置 HTTP 代理环境变量，因此不涉及 `NO_PROXY`。

**ntfy 侧。** topic 在首次发布时由服务端自动创建，无需预建；topic 名大小写敏感。若服务端开启了 `auth-default-access: deny-all`，token 所属用户需要对 `RSSGen` 拥有写权限（`ntfy access <用户> RSSGen write`，或在 `auth-access` 中声明）。

**中文标题经 HTTP 头传输。** shoutrrr 的 ntfy 服务把标题作为 `Title` 请求头发送。ntfy 服务端支持 UTF-8 请求头，也支持 RFC 2047 编码。实现完成后需对真实 ntfy 实例发送一次，确认中文标题显示正常；若出现乱码，改为在 URL 中填写 RFC 2047 编码后的标题，代码不变。

## 测试决策

好的测试只验证外部可观察的行为：给定配置，通知器是否构建成功；触发告警后，目标端是否收到了符合契约的请求。不断言 shoutrrr 内部结构或路由细节。

测试接缝沿用现有的，不新开：

- **通知器层**：现有测试用本地 HTTP 测试服务器模拟飞书。改为模拟 ntfy，URL 形如 `ntfy://127.0.0.1:<端口>/RSSGen?scheme=http&token=...`，断言请求路径为 topic、鉴权头携带 Bearer token、请求体为告警正文。另覆盖：非法 URL 使构造失败；`enabled: false` 时不发送；目标端返回错误时不 panic、只记日志。飞书无法指向本地测试服务器（lark 校验主机名），不单独测试飞书，其正确性由 shoutrrr 自身的测试保证。
- **运行时构建与 feed 处理层**：根目录现有两处测试使用了飞书服务配置——运行时构建测试、业务错误触发通知并熔断的测试。前者改为用 `service_urls` 配置一条 ntfy URL；后者改为用指向本地测试服务器的 ntfy URL，并继续断言测试服务器收到了请求。

随旧实现一同删除的测试：手写飞书发送器的全部测试（签名、请求体、各类错误响应），以及「未知服务类型被跳过」的测试。旧形态是主动删除的，不保留对它的断言。

按项目既有约定，新增测试只覆盖主路径和本次明确要求的行为，不为假设性的边界扩展测试矩阵。测试只用标准库，不引入断言库。

**验收标准：**

- `go build ./...`、`go vet ./...`、`go test ./...` 全部通过。
- 依赖中出现 `github.com/nicholas-fedor/shoutrrr`，代码中不再有飞书发送器及 `type` 分派。
- 本地用一份含非法 URL 的配置启动服务，进程以非零码退出，错误信息含出错 URL 的序号，不含 URL 原文。
- 部署后人为触发一次业务错误，ntfy 的 `RSSGen` topic 收到标题为中文且显示正常、优先级为 4、带 ⚠️ 标签的推送；飞书同时收到与改动前格式一致的纯文本消息。

## 范围之外

- 告警的触发条件、去重与频率限制：仍是每次业务错误熔断触发一次，不变。
- 熔断与健康状态模块的重构：架构评审清单中已有独立条目。
- `business_error_codes` 从 `notifier` 下迁出：它实际属于健康状态模块，但与本次无关，不动。
- 除飞书与 ntfy 之外的渠道：shoutrrr 已支持，配置即可使用，但不在本次验证与文档范围内。
- 在仓库 compose 文件中写死 ntfy 的网络。
- ntfy 服务端的部署、用户与 token 管理。

## 补充说明

- 选型依据（2026-10）：`nicholas-fedor/shoutrrr` v0.22.0 发布于 2026-10-13，持续维护；`containrrr/shoutrrr` 停在 2023-08 的 v0.8.0；`nikoksr/notify` 用 Go API 构造通知、不支持 URL 配置，且没有 ntfy。
- 上述关于发送参数校验、lark 主机名白名单与消息类型切换的判断，均以 shoutrrr v0.22.0 源码为准。升级该依赖时需重新核对这几点，尤其是「未声明参数会报错」这一条，它直接决定了 ntfy 专属参数必须放在 URL 里。
