# backfill 子命令拆分与历史条目重刷

## 问题陈述

知乎 2020 年前后的「想法」使用一种旧的转发卡片格式，其 content block 的 `type` 为 `link`（字段为 `title` / `subtype` / `link_type` / `url` / `image_url`），与当前代码支持的 `link_card`（字段为 `data_draft_title` / `data_content_type` / `url`）是两套结构。想法渲染器先看 block 自带的 `content` 字段，非空就直接采用、完全不看类型；旧版 `link` block 没有这个字段，于是落到类型分支，因类型不被识别而整块丢弃，只留下正文文本。读者看到的是一条凭空点评、不知道在评论什么内容的想法。

问题的规模无法从日志得知。日志里的告警只有 8 条，但那只是最近一次回填扫描窗口内的采样：告警是渲染那一瞬间打印的，此前经后台刷新正常推送、早已落进 Miniflux 的条目同样会静默丢失 link block，而那些日志早已滚没。仅目标 feed 就有 332 条想法，其中 2020–2022 年的 277 条正文里一个链接都没有——这是嫌疑的粗超集，真实受损集合只能靠重新抓取上游、检查原始 block 才能确定。

修复渲染器不能自动修复历史。Miniflux 的条目导入接口在条目已存在时只返回 200 且不改动任何内容，而回填的对账逻辑更是在候选条目命中现有 URL 或哈希时就直接跳过，根本不会发出请求。Miniflux 也没有删除单条条目的接口，只能删除整个订阅源，那意味着丢失该订阅全部已读与收藏状态。历史条目因此被永久钉在导入当天的渲染结果上。

上述关于 Miniflux 行为的判断以部署实例自报的 **2.3.3** 版本为准，依据该 tag 上的路由表与条目模型：条目更新接口存在且只接受标题与正文两个字段，两者均为空值时不赋值；条目导入在条目已存在时不改动内容；不存在删除单条条目的路由。升级 Miniflux 后需重新核对这几点。

与之并存的第二个问题是回填命令的参数已经过载：单个命令挂着十个 flag，而实际执行哪种操作由 `--list-feeds` 和 `--dry-run` 的组合隐式决定。列出订阅源时，feed ID、类别过滤、扫描游标、条数上限这四个参数全都无意义。它们并非可以蒙混过关——配置解析里有一串手写的「列出订阅源不接受某某参数」分支逐个拦截——但这正是问题所在：本该由命令边界表达的约束，被摊成了运行时校验代码，而这些参数仍与执行类参数共处同一份帮助文本，读帮助的人看不出哪些参数属于哪种操作。参数集合无法随语义收窄。

## 解决方案

把回填命令按语义拆成三个子命令，并新增一种「重刷」操作：

- **list**：列出该数据源下可回填的订阅源。必填的业务参数只有数据源与 Miniflux 地址两个。
- **execute**：将数据源历史中 Miniflux 缺失的条目补进去。即现有行为，两个数据源都支持。
- **refresh**：给定订阅源与时间范围，用当前渲染逻辑重新生成该范围内已有条目的标题与正文，并覆盖写回 Miniflux。需要数据源显式声明支持，当前仅知乎支持——理由见实现决策。

重刷不试图识别「哪些条目坏了」。识别需要程序长期维护一份「当前已知渲染缺陷」的清单，这份知识会随每次渲染改动而失效。重刷的语义是「让这批条目与当前渲染逻辑一致」，它本身幂等，范围内一律覆盖，不需要事先判断。修复是否生效由使用者跑完之后查询具体条目来断言，不由程序自证。

修复本身是在想法渲染器中补上 `link` 这一 block 类型，渲染为带类型标注的链接，形如 `[回答] 如何看待……`，链接指向 block 的 `url`。

## 实现决策

### 命令结构

回填命令拆为 `list`、`execute`、`refresh` 三个子命令。数据源、Miniflux 根地址、请求间隔这三个参数提升到父命令上——所用 CLI 库的 flag 默认下发给子命令，无需在各子命令重复声明。订阅源 ID、类别过滤、自我互动开关、扫描游标、条数上限、试跑开关归属 `execute` 与 `refresh`；`list` 不接受其中任何一个。

试跑保留为 flag 而非第四个子命令：它与执行的参数集合完全相同，只差写不写，拆开只会制造两份相同的 flag 列表。而 `list` 的参数集合与另外两者截然不同，这才是拆分的判据。

原有的 `--list-feeds` flag 随之删除，不保留向后兼容。旧形态的命令行会失效，需改写为带子命令的形式。兼容层要长期携带两套参数校验与两条测试路径，代价高于一次性改写命令行。项目自述文件中多处使用旧语法举例，须一并迁移——不保留兼容就意味着不能留下已经失效的用法示例。

需要注意提升到父命令的参数会被三个子命令一并继承，请求间隔对列出订阅源没有意义但仍会出现在其帮助里。列出订阅源所需的必填业务参数是数据源与 Miniflux 地址两个，这与「它只接受两个 flag」不是一回事；同时它仍然需要 Miniflux 的凭证环境变量，但不应因为父命令的存在而要求上游数据源的 Cookie。

### 扫描范围

新增扫描下界参数 `--stop-after`，与已有的上界 `--start-before` 构成一对。取值复用上界的解析逻辑，同时接受 13 位起的毫秒游标与日期（`YYYY-MM-DD` 或 RFC3339），因为定位历史位置时毫秒游标往往比日期更直接。

上下界都作用在**扫描侧**而非 Miniflux 侧：知乎动态按毫秒游标从新往旧翻页，若把范围只用于过滤 Miniflux 条目，扫描量与不加范围完全相同，时间窗只省下写入不省请求，而请求才是这里唯一昂贵的资源。下界透过数据源的构造参数传入，翻页过程中一旦越过即停止。

下界的比较对象是**动态自身的数值游标**，与上界所用的游标同一量纲，也与现有的续扫游标取自同一字段。不使用条目的发布时间：对点赞、收藏这类动态，被引用目标的创建时间可能远早于动态本身，用它提前停止会漏掉范围内的动态。该游标在解码结构上允许缺失或为零，现有测试夹具中就有不带该字段的动态，因此必须明确定义无有效游标时的行为——报错停止，而不是把「未知」当成「早于下界」，后者会让扫描在第一条就误判越界而静默返回空结果。越界判断在页内逐条进行：命中下界时裁掉该页剩余条目并结束翻页，而不是先整页收下再决定不请求下一页。

需要说明的是，「没有下界就会一直翻到最早的历史」只在不加其他限制时成立。知乎的翻页在达到条数上限、下一页地址重复、返回空页或上游标记结束时都会停止，命令层的条数上限还有非零默认值。下界的意义是让请求量与给定范围成正比，而不是它是唯一的刹车。

翻页函数新增下界参数后，同步请求与后台刷新路径的调用必须保持原有行为不变——它们与回填共用同一个翻页函数，回填的范围默认值不得渗进这两条路径。

`refresh` 必须至少给出 `--stop-after` 或 `--max-items` 之一，否则拒绝执行。这是不可逆写操作，而 Miniflux 没有单条条目删除接口，写错了只能再写一遍盖回去。给条数上限设默认值的方案被否决：那会让「没想清楚范围」与「确实要刷这么多」在命令行上长得一模一样。

这条校验的判定不能写成「条数上限大于零」或「条数上限被设置过」中的任意一个。条数上限本身已有非零默认值，前者会让默认值冒充显式选择；而该参数以零表示不限，后者会让显式传零绕过限制。判定必须是「给出了有效的下界，或显式给出了正整数条数上限」，同时保持补缺路径的默认值行为不变。上下界相等、上界早于下界、边界是否包含端点、日期取值的时区与精度也要一并定明——它们直接决定哪些条目会被写入，不属于假设性边界。已有的取值解析函数在错误信息里写死了上界的参数名，复用时需要让参数名可变，否则下界取值出错时会报出错误的参数名。

### 对账与写入

回填的条目结构新增 Miniflux 条目 ID 字段，条目查询相应多解析一个字段——覆盖写入需要这个 ID 定位。

对账逻辑改为同时产出两个集合：Miniflux 中缺失的候选条目，以及命中现有条目的候选条目（携带其 Miniflux 条目 ID）。`execute` 取前者，`refresh` 取后者。匹配规则不变，仍是链接相同或候选 ID 的哈希与条目哈希相同。

匹配从「是否命中」变成「命中哪一条」之后，必须补足两条此前不需要的规则。其一，链接与哈希可能命中不同的条目——已有测试就覆盖了「候选 ID 不同但链接相同」的情形，而想法的候选 ID 按类别生成，多条动态指向同一目标是可能的；规则定为哈希优先，因为它由候选 ID 直接导出，比链接更能确定是同一条动态。其二，多个候选可能命中同一个 Miniflux 条目；此时只更新一次，并在结果中计为一条，不允许由集合的遍历顺序决定最终写入哪份内容——重复命中按候选的既有排序取第一条。

运行入口的操作表示需要从单一枚举改为两个维度：执行哪种操作（补缺或重刷）与是否试跑。当前试跑是操作枚举的一个取值，只能表达「补缺的试跑」，无法表达「重刷的试跑」。范围校验放在入口而非仅放在命令层，因此范围参数需要随请求传入——只在命令层校验会让编排层无法对「缺少范围」这一约束做测试。

重刷分支加进现有的运行入口而非另起一个函数：订阅源解析、类别校验、读取现有条目、扫描历史、类别过滤这五步两条路径完全相同，拆成两个函数要么复制这段，要么抽出一个参数过多的内部函数。

Miniflux 适配器新增更新方法，签名接收条目 ID、标题、正文三个参数，而不复用导入用的条目结构。Miniflux 的条目更新接口只接受标题和正文两个字段，传入完整条目结构会让调用方误以为发布时间、状态等字段也会生效，而它们会被服务端静默丢弃——接口不应描述自己做不到的事。

重刷走与导入相同的正文获取流程，包括详情抓取与评论抓取，并保持「候选条目自带正文时优先采用」这一既有规则——不能无条件用详情结果替换正文，否则知乎的空操作详情会把扫描阶段已渲染好的正文清空。

**重刷需要数据源显式声明支持，当前只有知乎支持。** 爱发电走重刷会返回明确的不支持错误，而不是执行一个会损坏内容的流程。原因有三，任何一条单独成立都足以排除它：其一，同步请求路径会对爱发电正文做换行转换并追加列表接口返回的配图，而回填用的详情适配器两步都不做，候选条目在构造时就把配图字段丢弃了——照现状重刷图片动态会删掉正文里的配图并合并段落，这是实打实的数据损失；其二，爱发电的历史适配器没有任何范围参数，扫描固定不设上限，且其分页游标与知乎的毫秒游标不是一个量纲，上一节那条强制范围的约束在它身上无法兑现；其三，目标订阅源有两万余条条目，正文与评论各需一次请求，在范围约束缺位的前提下全量重刷是四万次量级的上游请求。

这与「重刷必须走完整正文流程」并不矛盾：那条决策要防的是「报告成功却什么都没做」，而爱发电即便走了完整流程也会损坏内容，明确拒绝正是同一条原则的正确延伸。补齐爱发电需要改动候选条目结构、详情渲染、分页范围三处，各自都要独立验证，作为后续独立一步处理。

评论抓取最终失败时，重刷**跳过该条、不写入**，并计入失败清单。这与补缺路径的处理刻意不同：补缺时评论失败只意味着新条目少了评论，重刷时却会用不含评论的新正文覆盖掉 Miniflux 里原本已有的评论。同一种失败在两条路径下后果不同，处理方式就不该相同。另需把用户取消导致的错误与可容忍的评论失败区分开，前者不应记为普通告警，否则输出会把「被中断」显示成「评论抓取失败」。

重刷同时覆盖标题与正文。只同步正文会留下标题与正文出自不同代码版本的条目，日后排查比完全没刷更难判断。

重刷忽略扫描范围内 Miniflux 不存在的条目，不顺手导入。补缺是 `execute` 的职责，两个子命令各管一件事正是这次拆分的意义。两件都要做就先后各跑一次。

试跑模式下，重刷输出待更新条目的 Miniflux 条目 ID 与链接清单，而不只是数量。这是本次修复的验收手段。

### 渲染修复

想法渲染器新增 `link` block 类型分支，渲染为指向 block `url` 的链接，链接文本为类型标注加标题，形如 `[回答] 标题`。标题为空时回落到 URL。block 结构相应新增标题与类型标注两个字段。

`link` block 中还有一个内嵌 JSON 字符串的卡片字段，被引用内容已删除时其中会写明原因，但标题与链接仍然保留。渲染只取标题与链接，不解析该字段。

配图字段不渲染：实测这批旧格式想法的配图字段均为空，为此写渲染逻辑等于为假设场景编码。

未知 block 类型的告警保持不变，以便下一种新格式出现时仍会暴露。

## 测试决策

好的测试只验证外部可观察的行为——命令接受什么参数、发出什么请求、写回什么内容——而不断言内部调用顺序或私有结构的形状。

三个测试接缝全部沿用现有的，不新开：

- **回填编排层**：现有测试通过假数据源与假目标端驱动运行入口。重刷分支的编排在此测试：范围参数缺失时拒绝执行、数据源未声明支持重刷时拒绝执行、试跑不产生写入、只更新命中现有条目的候选、跳过 Miniflux 中不存在的条目、标题与正文一并送出、评论最终失败时整条不写入、更新计数正确、中断后保留已写入部分。假目标端跟随接口新增一个更新方法，记录收到的条目 ID 与内容。注意仓库里有两处假目标端实现（编排层测试与知乎回填测试各一份），接口新增方法后两处都要补，否则无法编译。
- **Miniflux 适配器层**：现有测试用本地 HTTP 测试服务器断言请求契约。更新方法在此测试：请求方法与路径、鉴权头、请求体字段、成功与失败状态码的处理。
- **知乎路由层**：现有测试同时使用本地 HTTP 测试服务器与可替换的抓取函数字段。`link` block 的渲染在此测试：渲染出的链接文本与地址、标题为空时回落到 URL、不再产生未知类型告警；翻页下界在此测试：越过下界后停止请求。

除上述三处，命令层的既有测试也必须跟着迁移：现有测试断言了旧命令语法的接受与拒绝条件，以及帮助文本内容，子命令拆分后这些断言应改为验证新语法，而不是保留对旧语法的期待——旧形态是主动删除的，不是需要兼容的。

**验证时不能直接跑全量测试。** 爱发电路由有一个既有测试起了本地测试服务却没有替换主机地址，实际会对线上接口发起请求，且其断言无论成功失败都不会失败。这个问题已记录在架构评审清单中，本次不顺手修复，但验证必须按包或按测试名选择性执行，避免消耗上游配额。（2026-09-09 补记：该测试已修复，全量测试不再对线上发请求，此限制已解除。）

按项目既有约定，新增测试只覆盖主路径、本次明确要求的行为，以及已经复现的问题（旧格式 block 被丢弃）。不为假设性的边界扩展测试矩阵。

测试只用标准库，不引入断言库，与现有测试保持一致。

## 范围之外

- 不改动后台刷新调度器与 RSS 同步请求路径的任何行为，本次只影响回填命令与想法渲染。
- 不为重刷维护任何持久化状态，不记录哪些条目已刷过、哪些渲染缺陷已修复。
- 不识别「受损条目」，不在 Miniflux 侧做内容比对——服务端存储的是它自己消毒之后的 HTML，与本地渲染结果是否逐字节相等取决于内容本身（已经合规的片段可能原样保留，含被消毒属性的则不会），因此比对结果不可靠，作为写入判据会在难以预测的条目上退化为全量写入。
- 不支持一次重刷多个订阅源。不同订阅的时间范围各不相同，批量执行要么共用一个过宽的窗口白扫大量页面，要么得为每个订阅配一套参数。
- 不解析 `link` block 的内嵌卡片字段，不渲染其配图。
- 不新增删除 Miniflux 条目的能力，Miniflux 本身也未提供该接口。
- 不让爱发电支持重刷，因而也不在本次补齐它的三处缺口：候选条目保留配图字段、详情适配器补上换行转换与配图追加、历史适配器接通范围参数（其分页游标与知乎不同量纲，日期范围需另行换算）。补缺路径不受影响，照常工作。
- 不修复爱发电路由那个起了本地测试服务却仍对线上发请求的既有测试，只在验证时避开它。该问题已记录在架构评审清单中。（2026-09-09 补记：已在后续单独修复。）
- 不处理上游已删除的动态：它们不会出现在扫描结果中，因而不会被重刷，其 Miniflux 条目保持原样。

## 补充说明

知乎想法 ID 可反推发布时间，关系约为 `发布时间 ≈ (ID >> 22) / 1000 + 1292780000`（秒），用抓包样本中五条想法标定，误差约 ±130 秒。定位历史条目的大致游标位置时比翻日志更快。

从宿主机直接访问 Miniflux 时，若宿主配置了 HTTP 代理，需绕过代理，否则请求会被转发至代理并返回 502。这与部署文档中记录的容器内服务名需加入代理排除列表是同一个坑的两面。

爱发电的目标订阅源有两万余条条目，其正文与评论各需一次上游请求。这个数字是本次排除爱发电重刷的理由之一，也是将来补齐它时必须先接通范围参数的原因——在范围约束缺位的前提下，一次全量重刷是四万次量级的上游请求。
